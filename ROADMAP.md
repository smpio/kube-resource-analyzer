# Roadmap

Состояние на 27 сентября 2026 года. Документ разделяет реализованные возможности,
проверенное поведение и предложения по развитию. Дальнейшие этапы пока не утверждены;
сроки и обязательства не назначены.

## Цель и границы проекта

Помочь эффективнее использовать ноды Kubernetes через подбор `memory limits` и
`CPU requests` для контейнеров по фактическому потреблению и событиям OOM.
Рекомендации должны уменьшать избыточное резервирование ресурсов и учитывать риск
нехватки памяти. Эффект на загрузку нод и стабильность приложений ещё нужно измерить.

В текущем алгоритме память подбирается по максимуму потребления и зарегистрированным
OOM с запасом, CPU — по среднему потреблению с коэффициентом. Используются границы
отклонения от целевых значений; рекомендации содержат причины и приоритет.

Уплотнение размещения подов, перевод нагрузок на preemptible-ноды и autoscaling
остаются вне целей проекта, как указано в [README](README.md).

## Что реализовано

| Возможность | Реализация и границы |
| --- | --- |
| Сбор данных | Отдельные сборщики [pods](kra/collectors/pods.py), [metrics](kra/collectors/metrics.py) и [OOM](kra/collectors/oom.py). OOM-сборщик обрабатывает события `NodeOOM`; полнота обнаружения всех случаев нехватки памяти отдельно не подтверждена. |
| История и статистика | [Модели БД](kra/models) хранят workloads, поды, контейнеры, потребление и OOM. [Аналитика](kra/analytics/container.py) вычисляет максимумы, средние и стандартные отклонения; используются сводки по контейнерам и workloads. Хранилище — PostgreSQL/TimescaleDB. |
| Рекомендации | [Расчёт](kra/tasks/make_suggestion.py) предлагает memory limits и CPU requests. Команда [get_suggestions --update-all](kra/management/commands/get_suggestions.py) обновляет сводки и рекомендации. |
| Реакция на OOM | [Обработчик сохранения OOM](kra/signal_handlers.py) ставит пересчёт рекомендации в Celery; при создании записи также ставит задачу создания Kubernetes Warning event `ContainerOOM`. Прямого запуска применения adjustment из этого обработчика нет. |
| API и интерфейс | [Django API](kra/views.py) предоставляет историю, сводки, рекомендации и adjustments. [React UI](../kra-frontend/src/components) показывает нагрузки, данные и графики; содержит действия `Apply now` и `Apply tonight`. |
| Применение изменений | Создание или обновление adjustment через API запускает [задачу Celery](kra/tasks/apply_adjustment.py). Есть немедленное и отложенное выполнение, блокировка одновременной обработки, проверка наличия результата и запись успеха либо ошибки Kubernetes patch. Это наличие механизма в коде, а не подтверждение его надёжности во всех сценариях. |
| Обслуживание | [cleanup](kra/management/commands/cleanup.py) удаляет устаревшие записи и выполняет просроченные adjustments без результата. В [манифестах](../infra/kube/kube-kra) описаны TimescaleDB, Redis, три сборщика, Celery и CronJob для cleanup и пересчёта рекомендаций. |

## Что проверено и что остаётся непроверенным

По результатам предыдущей проверки окружения сервисы, включая Celery, уже работают
в кластере. Локальный backend в PyCharm и UI в VS Code успешно запускались:
API и UI отвечали HTTP 200, отображались реальные данные и графики. Порядок запуска
описан в [DEVELOPMENT.md](DEVELOPMENT.md).

В той проверке Apply не выполнялся. Сквозной путь от действия в UI до изменения
workload, корректность отложенного выполнения, обработка сбоев и восстановление
прежних ресурсов ещё требуют проверки. Наличие работающего Celery само по себе
не подтверждает эти сценарии. Автоприменение рекомендации сразу после OOM в
просмотренном коде не обнаружено.

В README заявлено обнаружение утечек и высокой волатильности потребления.
В коде есть статистика разброса, но отдельные детекторы с критериями срабатывания
и диагностическим результатом не найдены. Эти возможности пока не считаются
подтверждённо реализованными.

## Предлагаемые дальнейшие этапы

Порядок ниже — предложение для обсуждения, а не утверждённый план.

### 1. Проверить качество рекомендаций на истории

Статус: отложено. Историческая БД очищена, поэтому сейчас нет данных для
сопоставления рекомендаций с последующим потреблением и OOM. Подготовлена
read-only команда `check_adjustment_quality` для будущего анализа успешно
применённых adjustments; возвращаться к этапу следует после накопления
достаточной истории и выбора workloads для проверки.

Сопоставить рекомендации с последующим потреблением и OOM на выбранных workloads.
Рассмотреть пики, короткую или неполную историю, изменение характера нагрузки и
устаревшие OOM. Оценить коэффициенты запаса и границы срабатывания.

Ожидаемый результат: примеры удачных и ошибочных рекомендаций, согласованные
критерии качества и способ измерять экономию ресурсов и риск OOM.

### 2. Проверить применение, ошибки и откат

На согласованной тестовой нагрузке проверить цепочку UI → API → Celery → Kubernetes
для немедленного и отложенного применения, повторной обработки и ошибок API.
Отдельно проверить согласованность сводок с реальными ресурсами после неудачного
patch: сейчас код обновляет сводки и удаляет рекомендации даже после записи ошибки.
Проверить сохранность остальных настроек ресурсов, поскольку patch заменяет весь
объект `resources` контейнера.

Определить способ сохранения прежних значений и восстановления после неудачного
изменения; готовый механизм автоматического отката не подтверждён.

Ожидаемый результат: воспроизводимая проверка применения и восстановления,
перечень необходимых исправлений и понятный пользователю статус операции.

### 3. Учитывать Argo CD при применении resources

Перед применением изменения проверить аннотацию
`argocd.argoproj.io/tracking-id` у изменяемого объекта. Если она есть, по её
связи с приложением получить через Kubernetes API объект `Application` группы
`argoproj.io`, затем взять из него `spec.source.repoURL` и `spec.source.path`.
В указанном пути репозитория найти манифест того же Kubernetes-объекта и
контейнер, для которого выполняется adjustment.

Если в найденном манифесте для этого контейнера уже объявлен `resources`,
изменять рекомендуемые requests/limits в Git-манифесте, а не патчить объект в
кластере. Следует точно сопоставлять объект по API-группе, kind, namespace и
имени, не менять шаблоны или файлы, которые относятся к другому объекту, и
сохранять остальные поля `resources`.

Если манифест найден, но `resources` в нём не указан, сохранить текущее
поведение — применить изменение напрямую через Kubernetes API. Это исключение
не следует распространять на другие ошибки: отсутствие или неоднозначность
`Application`, недоступность репозитория, невозможность найти манифест или
контейнер должны завершать операцию понятной ошибкой без прямого patch, чтобы
не создать расхождение GitOps-состояния и кластера.

Нужно отдельно определить аутентификацию к приватным репозиториям, работу с
`targetRevision` и способом доставки коммита/PR, поддержку Helm/Kustomize и
права RBAC на чтение `Application`. В результате операции UI должен явно
показывать, где выполнено изменение: Git-манифест, ожидающий синхронизации Argo
CD, либо непосредственно кластер.

Ожидаемый результат: проверенный сценарий для Argo CD-управляемого workload,
который обновляет существующие resources в исходном репозитории и не допускает
тихого обхода GitOps при ошибках разрешения источника.

### 4. Обновить Python до последней стабильной версии

Выполнено в конфигурации и документации:

- [x] Базовый production-образ переведён на Python 3.14.7 — последний стабильный
  релиз на 27 сентября 2026 года.
- [x] Инструкция разработки ссылается на образ и ограничивает Django совместимой
  веткой 5.2 (не ниже 5.2.8); проверка версии в `python-utils` также ожидает Django 5.2.
- [x] Установка Django 5.2.17 и остальных текущих зависимостей проверена в чистом
  окружении Python 3.14.7.
- [x] CoreAPI-код в `python-utils` заменён встроенной OpenAPI-схемой DRF; endpoint
  `/swagger.json` возвращает корректную OpenAPI 3.0.2 схему.
- [x] На Python 3.14.7 выполнены `manage.py check`, тесты и проверка зависимостей.
- [x] Проверены реальные внешние сервисы: TimescaleDB 2.6.0, таблица
  `kra_workload`, Redis PING и read-only вызов Kubernetes API новым Python-клиентом.
- [ ] Восстановить Celery и сборщики в кластере: текущий Deployment использует старый
  образ на Python 3.9 и падает на проверке Django 4.0. После публикации и развёртывания
  нового образа проверить worker и выполнение задачи без изменения workload.
- [x] Добавлены воспроизводимые lock-файлы для production и development окружений
  на Python 3.14.7.
- [x] Production-образ собран из lock-файла и прошёл `manage.py check`.

Django 5.2 официально поддерживает Python 3.14, начиная с 5.2.8. Поэтому до
успешного прогона проверок этап нельзя считать полностью завершённым, но выбранные
ветки Python и Django совместимы.

### 5. Определить правила и ограничения автоматизации

После проверки качества и применения решить, какие изменения требуют ручного
подтверждения и где допустимо автоприменение. Обсудить разрешённые workloads,
минимальную полноту истории, пределы изменения ресурсов, интервалы между
изменениями, реакцию на OOM и условия остановки автоматизации.

Ожидаемый результат: утверждённые правила допуска и контроля. Само наличие
рекомендации или события OOM пока не означает разрешения на автоматическое изменение.

### 6. Рассмотреть детекторы утечек и нестабильности

Уточнить, какие признаки отличают утечку от обычного роста нагрузки, а нестабильность
от ожидаемых пиков. Проверить возможные детекторы на истории и оценить ложные
срабатывания, прежде чем связывать их с изменением ресурсов.

Ожидаемый результат: решение о необходимости детекторов, критерии проверки
и формат объяснения результата в UI. Автоперезапуск подов этим этапом не обещается.
